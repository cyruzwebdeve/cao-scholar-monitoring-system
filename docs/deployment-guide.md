# Free Capstone Deployment Guide

This project is prepared for the following deployment layout:

- **Frontend:** Vercel Hobby, using `frontend` as the project root
- **Backend API:** Render Free Web Service, using the root `render.yaml`
- **Database:** Prisma Postgres provisioned through the Vercel Marketplace
- **Files:** one private Vercel Blob store for scholar documents and one public
  Vercel Blob store for announcement images

This arrangement keeps database credentials and Blob tokens on the backend.
Never create a frontend variable named `VITE_DATABASE_URL` or place a Blob
read/write token in a `VITE_` variable.

## 1. Create the Vercel frontend project

1. Import `cyruzwebdeve/cao-scholar-monitoring-system` into Vercel.
2. Set the project **Root Directory** to `frontend`.
3. Keep the detected Vite build command (`npm run build`) and output directory
   (`dist`).
4. Deploy once to reserve the production URL. API calls will not work until the
   Render service and `VITE_API_BASE` are configured.

The included `frontend/vercel.json` preserves React Router routes when a page is
opened or refreshed directly.

## 2. Provision Prisma Postgres

1. In Vercel, open **Storage**, create a database, and select **Prisma
   Postgres** from the Marketplace.
2. Choose the free plan and a region near the Render service.
3. In the Prisma Console, generate both connection strings:
   - the **pooled** URL for normal application traffic;
   - the **direct** URL for migrations and Prisma Studio.
4. Keep both values private. They will be entered in Render as `DATABASE_URL`
   and `DIRECT_URL` respectively.

The backend uses the pooled URL at runtime. Its deployment migration script
temporarily uses only `DIRECT_URL`, which avoids migration failures through a
connection pooler.

## 3. Create the Blob stores

Create two Vercel Blob stores:

1. A **private** store for scholar requirement documents. Copy its read/write
   token for `DOCUMENT_BLOB_READ_WRITE_TOKEN`.
2. A **public** store for announcement images. Copy its read/write token for
   `ANNOUNCEMENT_BLOB_READ_WRITE_TOKEN`.

Production uploads fail safely with a configuration message if the applicable
token is missing. Local development can continue storing base64 test uploads in
the local database, so the cloud tokens are optional locally.

## 4. Deploy the Render API

1. In Render, create a **Blueprint** from the GitHub repository.
2. Render will detect `render.yaml` and create
   `cao-scholar-monitoring-api` on the free plan.
3. Enter the requested secret values:

| Variable | Value |
| --- | --- |
| `DATABASE_URL` | Prisma Postgres pooled connection string |
| `DIRECT_URL` | Prisma Postgres direct connection string |
| `CORS_ORIGINS` | Vercel frontend URL, with no trailing slash |
| `DOCUMENT_BLOB_READ_WRITE_TOKEN` | Private Blob store token |
| `ANNOUNCEMENT_BLOB_READ_WRITE_TOKEN` | Public Blob store token |
| `GMAIL_USER` | Gmail address used to send applicant lifecycle updates |
| `GMAIL_CLIENT_ID` | Google Desktop OAuth client ID |
| `GMAIL_CLIENT_SECRET` | Google Desktop OAuth client secret |
| `GMAIL_REFRESH_TOKEN` | Offline token authorized only for `gmail.send` |
| `MAIL_FROM_NAME` | Display name, normally `PGCEAP Community Affairs Office` |
| `APP_BASE_URL` | Vercel frontend URL, with no trailing slash |
| `BOOTSTRAP_ADMIN_EMAIL` | Initial super administrator email |
| `BOOTSTRAP_ADMIN_PASSWORD` | A temporary password of at least 12 characters |
| `BOOTSTRAP_BILLING_ADMIN_EMAIL` | Optional initial Billing/Payroll Admin email |
| `BOOTSTRAP_BILLING_ADMIN_PASSWORD` | Optional temporary Billing/Payroll Admin password of at least 12 characters |
| `BOOTSTRAP_MODERATOR_EMAIL` | Optional initial Content Moderator email |
| `BOOTSTRAP_MODERATOR_PASSWORD` | Optional temporary Content Moderator password of at least 12 characters |

`JWT_SECRET` is generated by the Blueprint. `DATABASE_TARGET=cloud` makes the
backend use the managed database name exactly, without the local `_v2` suffix.

During the first build, Render generates Prisma Client, applies committed
migrations, creates the active `2026-2027 / 1st Semester` period, and creates any
configured administrator accounts that do not already exist.

After the accounts are created, remove `BOOTSTRAP_ADMIN_PASSWORD`,
`BOOTSTRAP_BILLING_ADMIN_PASSWORD`, and `BOOTSTRAP_MODERATOR_PASSWORD` from
Render, then deploy again. The email and optional name variables may remain;
without their temporary passwords, bootstrap safely skips account creation. It
is idempotent and never replaces an existing administrator password or role.

### Gmail lifecycle mailer

The API sends an account-creation email after a new application, an examination
receipt after the applicant submits an exam, and an approval email when the
applicant becomes a scholar. Email delivery happens after the database change;
an unavailable mail service does not undo a submitted application or status
update.

Render Free blocks outbound SMTP ports, so production sends through the Gmail
HTTPS API instead of Gmail SMTP. In Google Cloud, enable the Gmail API, configure
an External OAuth app, add only the `gmail.send` sensitive scope, add the sender
account as a test user, and create a Desktop OAuth client. Download its JSON and
run the following command locally without moving the file into this repository:

~~~powershell
npm --prefix backend run gmail:authorize -- "C:\path\to\downloaded-client.json"
~~~

Open the printed Google authorization URL using the sender account. The local
callback writes `GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET`, and
`GMAIL_REFRESH_TOKEN` to the git-ignored `backend/.env.gmail.generated` file.
Copy those values directly into Render without sharing them, close the file,
and delete it immediately afterward. The helper requests offline access with
PKCE and only the `https://www.googleapis.com/auth/gmail.send` scope.

An External OAuth app left in Testing issues refresh tokens that expire after
seven days. Before the final presentation, publish the OAuth app to Production
or repeat local authorization whenever the testing token expires. After saving
the Render variables and redeploying, verify them locally with
`npm --prefix backend run mailer:verify`, or submit a test application using an
email address you control. If the API credentials are absent, the backend may
use the App Password SMTP fallback locally or on paid hosts that permit SMTP.

## 5. Connect Vercel to Render

1. Copy the Render service URL, for example
   `https://cao-scholar-monitoring-api.onrender.com`.
2. In the Vercel frontend project, add:

   `VITE_API_BASE=https://your-render-service.onrender.com/api`

3. Apply it to Production and Preview as needed, then redeploy the frontend.
4. If a Vercel preview domain must access the API, add its exact origin to
   Render's comma-separated `CORS_ORIGINS` and redeploy the API.

## 6. Verify the deployment

1. Open `https://your-render-service.onrender.com/api/health`. It should report
   `healthy` and `database: connected`.
2. Sign in with the bootstrap administrator account.
3. Submit a test application and confirm its applicant-account email arrives.
4. Create and expire a test announcement.
5. Upload a small test scholar requirement and verify the record remains after
   a Render restart.
6. Open applicant, scholar, examination, billing, payroll, announcement,
   report, and settings pages once to confirm API access.

Render Free services sleep after inactivity, so the first API request may take
about a minute. This is acceptable for a capstone demonstration, but it should
be explained during testing. Stored records and uploaded files remain safe
because they live in Prisma Postgres and Vercel Blob rather than Render's local
filesystem.

## Local commands retained

Local development is unchanged:

~~~powershell
npm run dev
npm --prefix backend run prisma:studio
~~~

For Prisma Studio against the cloud database, temporarily set both local
database variables to the direct connection string and set
`DATABASE_TARGET=cloud`. Never commit those credentials.
